The master key is **not** bound to user authentication (`setUserAuthenticationRequired` is absent),
so app lock does not gate the ciphertext against an attacker running code as the app.

### 2.6 Transports — **W**

| Subfeature | Files | St |
|---|---|---|
| WebRTC data channel | `transport/rtc/RtcTransport.kt`, `RtcDataSession.kt`, `RtcState.kt`, `RtcSignalCodec.kt` | W |
| Direct TCP server + client | `transport/TcpMessageServer.kt`, `MessageSender.exchangeFrame` | W |

| Seams | `transport/FrameInbox.kt`, `transport/rtc/PeerTransport.kt` | W |
| IP-exposure policy | `transport/IpExposureGate.kt` | W |
| No-permitted-path status | `MessageSender.noDeliveryPath`, `ConversationViewModel.deliveryBlocked`, `ConversationScreen` banner | W |

Actual outbound order for a **text** message: RTC data channel → direct TCP (policy-gated) →
DERP blind relay → contentless tap. The relay is **opt-in and off by default**
(`AuroraSettings.relayEnabled`); when disabled the tap step is reached directly. The tap is
signalling only and is what wakes a backgrounded peer when the relay is off. For **media**:
RTC data channel → direct TCP. **There is no relay path for media at all**, and the TCP fallback
does not consult the IP-exposure policy.

When a message is still pending and the device has no *permitted* path for that contact
(policy forbids direct, relay off, no open RTC channel), `MessageSender.noDeliveryPath` records
the contact and the conversation shows a "not delivered" banner instead of a silent clock.

### 2.10 Groups — **X**

| Subfeature | Files |
|---|---|
| Creator-signed, hash-chained membership | `group/GroupManager.kt`, `group/GroupProtocol.kt` |

**Confirmed independently by two passes.** The only reference to this package from outside it is
the `GroupSealer` binding at `di/AppModule.kt:73`, and nothing injects `GroupSealer` — so Hilt
never even constructs `RatchetGroupSealer`. Zero `group` matches in `com/aura/ui`, no nav route,
no transport frame type. 23 tests exercise it.

Sealing is **pairwise fan-out** per recipient through the ordinary 1:1 ratchet. There is no shared
group key and no sender-key chain, so a group can only work if every pair already has a seeded
session. `group_members.kemPubB64` is never used to encrypt anything.

`res/values-ru/strings.xml` (305 + 2), `res/xml/locales_config.xml`.
Parity is enforced by `TranslationParityTest`. The three-key delta is exactly the
`translatable="false"` entries. The entire legal corpus is English-only regardless of locale.

## 8. Findings

Ordered by severity. Every item carries a `file:line`.

### 8.1 Security-critical

1. **`PrekeyManager.consume` ignores the prekey `kind`.** An OPK id presented as an SPK id
   deletes the current signed prekey; forward secrecy is void for attacker-chosen handshakes.
   `crypto/PrekeyManager.kt:85-91`.
2. **The Privacy Policy contradicts the implementation** on three points that matter: the server
   *is* in the path (DERP relay), nodeId *is* co-stored with IP, and the server *does* hold sealed
   frames and prekeys. `legal/LegalDocs.kt` §6 vs `transport/DerpTransport.kt`, `index.js:346,471`.
3. ~~**App lock can be removed without authentication.**~~ **Fixed 2026-10-29.** Disabling the
   lock, changing the real PIN, and replacing the decoy PIN now require the current real PIN
   (`AppLock.kt`); a wrong attempt counts toward the lockout, and `SecureWipe` uses an internal
   unguarded path because it runs after key destruction.
4. **The DB key is not bound to user authentication.** Default Keystore alias, no
   `setUserAuthenticationRequired`, no StrongBox — app lock is cosmetic against anyone who can run
   code as the app. `db/DbKeyStore.kt:19-29`.
5. **Wipe is incomplete and non-atomic.** Five group tables survive; no `VACUUM`, no
   `secure_delete`, no file overwrite. The DB key is cleared *before* the file is deleted, so a
   kill in between leaves an unopenable DB and a fresh key → permanent crash loop.
   `security/SecureWipe.kt:44-61`, `di/AppModule.kt:49`.
6. ~~**Media bypasses the IP-exposure policy and has no relay path.**~~ **Fixed 2026-10-29** in
   both directions: `media/MediaTransfer.kt` consults `IpExposureGate` before its outbound
   direct-TCP fallback and reports "no permitted path", and `handleIncomingTcp` refuses an
   inbound direct media socket before reading the payload when the contact may not have a
   direct path with us. TURN-relayed RTC media remains permitted. Media still has no relay
   path, by design. Inbound **text** over direct TCP is still ungated (follow-up).
7. **Call signals are accepted from any paired contact.** `ice`/`answer`/`bye` are not bound to the
   peer the call belongs to. `call/CallController.kt:374-389`.
8. **Pairing control frames are Ed25519-only.** A CRQC forgery of `contactremove` triggers
   `ContactEraser.wipe`. `pairing/PairingSignal.kt:26-27,50-53`, `ReceiverPairing.kt:169-173`.
9. **OPK signature failure silently downgrades forward secrecy.** The scanner drops the one-time
   prekey and pairs with IK+SPK only. `pairing/ScannerPairing.kt:196-201`.
10. **`POST /signal` is unauthenticated.** Anyone knowing a nodeId can inject frames and fill the
    64-slot queue. `index.js:381-403`.
11. **`/find` is a presence and IP oracle.** Padding is RFC1918-only, so a routable address stands
    out; the Kotlin server returns 404 for unknown nodes. `index.js:253-260,355`,
    `AuroraRendezvousServer.kt:187`.
12. **Relay targets come from unverified `/find` padding.** `mesh_peers` is seeded with the 9
    dummy candidates and `relayExchange` picks `relays.first()`. `MessageSender.kt:112,283-288`.
13. **Pre-auth message-id oracle.** `processMsg` re-acks a known id from a merely claimed `from`
    before any decryption. `TcpMessageServer.kt:155`.
14. **`FLAG_SECURE` is absent in debug builds**, including on the QR and PIN screens.
    `MainActivity.kt:58-59`.
15. **The pairing QR is written to public storage.** Defeats the screenshot posture and exports
    reachability addresses, not just keys. `ui/qr/MyCodeScreen.kt:132-153`.

### 8.2 Correctness and data loss

16. **Media never expires in disappearing chats.** Only text is stamped.
    `disappearing/DisappearingMessages.kt:52-56`.
17. **Re-pairing destroys all prior media.** A new random `mediaKey` is minted and the old one is
    lost with the overwritten ratchet blob. `KemRatchetManager.kt:58-59`.
18. **`status="sent"` is a terminal dead end** — never retried, never stamped with an expiry.
    `MessageSender.kt:180` vs `Messages.kt:89`.
19. **Restore failures are invisible.** The error is stored in a flow nothing observes.
    `SettingsViewModel.kt:37`.
20. **Identity silently regenerates** when any single identity pref is missing or undecodable,
    leaving contacts and ratchets from the old identity in place. `IdentityStore.kt:112-122`.
21. **No orphan collection.** A crash between the media write and the row insert leaves an
    unreferenced `.enc` forever. `MediaTransfer.kt:106-107,278-279`.
22. **Media metadata is unauthenticated** — `id`, `mtype`, `duration`, `ts` travel in cleartext
    under a constant AAD. `MediaTransfer.kt:187-196,308`.
23. **Control frames have no relay path**, so timer changes and reactions fail silently on hard NAT.
    `MessageSender.kt:261-263`.
24. **Deleted contact text persists** in SQLCipher free pages until the file is vacuumed.
    `db/ContactEraser.kt:21-31`.
25. **Peer identity change is not detected** — a new keypair is a new nodeId and the old ACTIVE
    row stays messageable. `db/Contacts.kt:119`.
26. **`restore()` merges rather than replaces**, and verification flags are not exported.
    `IdentityStore.kt:94-97`, `Backups.kt:111-124,150-157`.

### 8.3 Build and supply chain

27. **No dependency locking or verification.** No lockfile, no `verification-metadata.xml`, no

28. **The shipped crypto is an unverified committed jar.** Nothing proves `aura-crypto-0.1.0.jar`

30. **Release is unminified with no ProGuard file** — 83.8 MB APK, readable class names.

## 9. Reconciliation

**Conflict.** The database pass reported that `mesh_peers` has no production writer and is "only
ever deleted". The transport pass reported that `MessageSender` seeds it from `/find` candidates.

**Resolution.** The transport pass is correct. `MessageSender.kt:112` calls
`meshPeerDao.upsertAll(...)` with the nine non-returned `/find` candidates, and `:283` calls
`meshPeerDao.all()`. The database pass had visibility only into its own package. The table is
therefore written during a session and cleared at every launch by `StartupMigrations.kt:40` —
which is what makes ShadowMesh a scaffold rather than merely dead: it has a data source, and that
source is nine RFC1918 addresses that cannot be relayed to.

**Second correction.** An earlier revision of this document said "two group tables". There are
five: `groups`, `group_members`, `group_membership_events`, `group_messages`, `group_deliveries`.

**Third correction.** An earlier revision said media "only travels over direct TCP". It does not —
`MediaTransfer` prefers the RTC data channel. The accurate statement is that media has *no relay
fallback*, and its direct-TCP fallback now consults the IP-exposure gate (fixed 2026-10-29).
